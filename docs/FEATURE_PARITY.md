# Feature parity audit

Audit date: 2026-09-20. Reference: the local `../clash-verge-rev` checkout, commit `dfc9cc263035aa4a534720411de4a719481eaeda`. clash-qt baseline: `583c0f9ee9a7f3020c44fb42513f078becf559a4`. The status below includes the uncommitted audit fixes in this workspace; it is not a claim about the baseline commit or upstream releases.

**clash-qt is not yet a complete replacement for Clash Verge Rev.** The shared mihomo core supplies proxy protocols and routing, but it does not supply the surrounding service management, profile workflows, update distribution, desktop integration, diagnostics, or recovery UI. An external dashboard is useful access to core functionality, not evidence of native feature parity.

“Implemented” means the operation has a concrete application path in the audited code. “Partial” means the basic operation exists but reference workflows or supported environments are missing. “Missing” means no equivalent application implementation was found. The matrix records source coverage, not a guarantee that every feature works on every platform. macOS is the available validation environment; Windows, Linux, privileged TUN and external WebDAV servers still require environment-specific verification.

Priority: **P1** blocks a credible general-purpose replacement or a common workflow; **P2** is advanced functionality or a substantial usability gap; **P3** is optional customization. P0/P1 correctness defects discovered in existing implementations are tracked separately from absent features.

## Audit fixes and evidence

At the baseline, enhancement steps were never applied to runtime generation; switching/updating a profile did not update the managed core; endpoint changes left stale REST/UI state; a live app could leave its system proxy behind; several UI operations had no explicit refresh/search or in-app editing path. The workspace audit addresses these paths and adds provider management, scoped backups, runtime controls, overview/diagnostics and regression coverage. See the actual diff and test output for the final implemented extent; adding a page is not itself acceptance evidence for every feature in that page.

Focused tests added with this comparison:

- `tests/provider_test.cpp`: actual localhost HTTP fixtures verify provider counts/quota/expiry, omission of implicit Compatible providers, authentication, encoded provider names, GET healthcheck/PUT update routes, server failures, malformed JSON and delayed stale replies during A → B → A endpoint changes.
- `tests/backup_test.cpp`: profile/script/settings round-trip, controller-secret/cache exclusions, preservation of non-backed-up files, rollback after a partially installed restore, rejection of path traversal, case/Unicode aliases, Windows reserved paths, duplicates, checksums, missing references, oversize archives and symlink destinations before stopping the core. Localhost HTTP fixtures verify WebDAV upload/download, redirect rejection and invalid remote archives; no external account is used.
- Additional controller/core tests and visual review are maintained by the parallel audit tasks. Do not infer Linux/Windows, privileged service or real WebDAV verification from these tests.

## Remaining acceptance milestones

1. Implement and validate a privileged service lifecycle on each supported OS, including TUN enable/disable, rollback after failure, upgrade/uninstall and network transitions.
2. Establish distributable, signed/reproducible app/core packages and an authenticated update/rollback workflow. Verify an install on a clean machine with no Verge Rev, no development Qt installation and no preseeded geodata.
3. Make a deliberate compatibility contract for imported Verge Rev profiles, per-profile enhancements and sequence edits; test representative scripts/configurations rather than assuming engine substitution is equivalent.
4. Complete PAC/guard, structured core settings, configurable connection columns, runtime proxy chains, startup/tray workflows and diagnostics where full reference parity is required.
5. Complete backup schedules/remote history and migration; test restore during pending downloads and core reload, and verify recovery from failed filesystem/settings writes.
6. Run a platform matrix and visual interaction audit, including empty/error/loading states, dark/light theme, small windows, many profiles/providers/nodes, high traffic/log rates, reconnects and application shutdown.

Until those gaps are implemented and validated, the appropriate description is an improved native client with documented partial parity, not “complete Clash Verge Rev parity.”
